### Phase 1 — Measurements before building (de-risk the design)

**1.1 Ordering experiment.** Run v5 over the eval set under three orderings —
harness-top-last, harness-top-first, rotated — and measure. Settles spec §3.1 with data
instead of intuition. Cheap: existing model, existing candidate sets, GPU inference only.

**1.2 Baseline the current harness.** Measure danger-table coverage (now 17/32 arm-4
canonical commands), candidate-generation recall on real inputs, and passthrough latency.
These are the numbers spec §9 is compared against.

**1.3 Build the bake-off harness.** §10.5 needs a frozen 2,000-item draw and a
rotation-averaged scorer. Build once, before any teacher runs.

### Phase 2 — Harness implementation

Each item: failing test first, then implementation.

1. Front door — first-argument validity (spec §1.1).
2. Danger table expansion + flag heuristic (spec §2.1, §2.2).
3. Allowlist + deny list + policy store (spec §4).
4. Ordering rule (spec §3.1) — using the Phase 1.1 result.
5. Near-neighbor reconditioning + offer ring buffer (spec §5.2).
6. Daemon + fish integration — the riskiest piece; it touches the user's shell.
7. `nlaze allowlist` / `nlaze danger` CLI.

**Gate G1 — freeze the candidate/option format.** v6 training data is generated in the
harness's option format. A format change after generation forces regeneration. Freeze at
the end of Phase 2.

### Phase 3 — Eval and sandbox testing

**3.1 Build the v6 harness eval** — gold-in-shortlist, passthrough latency, danger coverage,
strike precision/recall, direct-serve latency (spec §9). The existing eval scripts are
model-oriented; the harness needs its own.

**3.2 End-to-end in the sandbox** — fish hook → daemon → correction → execution, in a VM or
container with no host mounts (spec §10).

**3.3 Separate harness issues from model issues.** Reuse the arm-2 methodology: hold the
candidate set fixed, vary one component at a time. Attribute each failure to harness
(retrieval, ordering, verifier) or model (selection).

### Phase 4 — Fix harness issues

Fix what 3.3 attributes to the harness. Re-run the eval after each fix.

### Phase 5 — Model

**5.1 Run the teacher bake-off** (§10.5) on the frozen draw; apply the pre-registered
decision rule.

**Teacher loader (resolved 2026-11-20).** The NVFP4 checkpoint (`granite-4.2-8b-nvfp4`)
cannot run on the 8 GiB RTX 5050: `compressed-tensors` decompresses all 8.79 B params to
bf16 on the first forward pass (~17.6 GiB). `scripts/convert_nvfp4_to_bf16.py` converts it
layer-by-layer to `models/teacher/granite-4.2-8b-bf16/` (16.38 GiB, 41 shards). Loading that
with `BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_quant_type="nf4",
bnb_4bit_compute_dtype=torch.bfloat16, llm_int8_skip_modules=["lm_head"])` peaks at
**5.81 GiB VRAM** and runs. The bake-off scorer (`scripts/bakeoff.py score --kind causal`)
implements §10.5.2: chat-template prefix, numbered option list, isolated-tokenisation option
spans, fp32 log-softmax over `lm_head` slices, PMI_DC null term, rotation-averaged.

**Local-only decision (2026-11-20).** No API-generated datasets. DeepSeek's terms permit
distillation, but the OpenCode gateway ToS restricts programmatic extraction and use of
Output to develop competing models, and the API does not expose prompt logprobs. Phase 5
uses the local Granite teacher exclusively; generated datasets are audited by subagents
before they enter training.

**5.2 Generate teacher outputs** over the training data in the frozen format (G1). Cache the
teacher's 7-option probability vector per training item (plus the permutation-stability flag
for the §3.5 gate). One pass, no rotations; the gate's stability check is a separate 6-rotation
sub-pass on the gated subset.

**5.3 Distillation experiment.** Conditional/gated per `research-distillation` §0.3. That
doc's own recommendation: if the ablation shows no top-1/top-3 retention, **ship the student
trained on data alone**. Pre-commit the kill criterion before running; a negative result is
a valid outcome.

**5.4 Fix model issues**, then re-run the harness eval against the v6 model.

**Why v1 is not obviously redundant:** its eval report claims 0.9878 accuracy / 0.0017 ECE,
higher than v5's 0.939 / 0.035. The eval sets differ (4,744 vs 6,438 items), so the numbers
are not directly comparable — the corpus grew and the later set is harder. Its train log also
shows `ce 0.0000` repeatedly, a degenerate-confidence signature worth understanding before
the checkpoint is discarded. Recommendation: keep v1 until the v6 eval harness can score it
on the same frozen draw as v5 (Phase 1.3), then decide.

Kept: `models/nlaze-base` (v5, shipped) and `models/laya-fp16` (training base, referenced by
`scripts/train.py`).

## 4. Risks

| Risk | Mitigation |
|---|---|
| USB failure loses untracked work | Phase 0.1, now |
| Disk exhaustion during download / training | Phase 0.2; 69 GiB ceiling on `/mnt/ssd` |
| Teacher too large for 8 GiB VRAM | VRAM frontier gate **before** download |
| Distillation does not beat v5 | Pre-committed kill criterion; fall back to data-only |
| Fish integration breaks the user's shell | Sandbox first; kill-switch; v1 observer pattern |
| Danger-table coverage gap | Phase 2.2; spec §9 does not claim the measure is met |
| Ordering rule guessed wrong | Phase 1.1 measures it before Phase 2.4 |

2. ~~Prune the redundant checkpoints?~~ **Partly done** (10 GiB freed). **Open:** whether to

3. **Is a larger teacher the primary path, or conditional distillation from v5?** The two
